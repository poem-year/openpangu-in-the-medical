# 正式测评集评测方案（L0 基线版）

> 更新：2026-09-13 ｜ 对象：`正式测评集/`（332 题 / 13 维度）
> 一句话：同一套题、同一批参数，批处理跑生成 → 自动判分 → 出报告；全量 L0 生成约 5 分钟（慢思考）。

## 一、为什么这么设计

测评集要求「能判分、能追溯、能复现」，所以方案把三件事拆开，各自可重跑：

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| 生成 | 按固定提示词批量跑模型，原始输出全部落盘 | `predictions.jsonl` |
| 判分 | 按题型用规则 / rubric 判分，逐题留证据 | `scores.jsonl`、`rubric_judgments.jsonl` |
| 报告 | 分维度汇总 + 四个上报指标 + 置信区间 | `summary.json`、`summary.md` |

## 四、判分口径

判分分三级（能自动的自动，判不准的才交给 AI）：

| 级别 | 适用 | 做法 | 成本 |
| --- | --- | --- | --- |
| 一级：规则精确判 | 单选、计算、yes/no 证据问答 | 选项/数值/标签精确比对 | 零 |
| 二级：规则快路 | 开放诊断、鉴别诊断 | 参考答案的核心诊断名（或全部鉴别条目）完整出现在回答里 → 直接判对 | 零 |
| 三级：AI 复核 | 上面两级判不了或不匹配的开放题，以及 D09–D11 的 rubric | DeepSeek 判「是否同一个诊断」，给 0 / 0.5 / 1 分 | API 调用（并发 6） |

一级判分（`eval/eval_lib.py: score_item`）：

- **单选**：先找「答案：X」，找不到就取末尾独立字母，与标准答案精确比对。
- **计算**：优先取「答案：」后的数字，其次取 `≈` / `=` 后的数字，最后取末行数字；容差 1% 或 0.01（取宽）。
- **证据问答**：结论按 yes / no / maybe 比对；检查 `[摘要N]` 是否落在给定材料范围内（引用可追溯率与幻觉率的来源）。
- **开放诊断 / 多轮问诊**：从 `key_points` 抽期望诊断名，与回答做相似度（包含关系 + 字符二元组 Dice + 最长公共子串）≥ 0.5 判命中。
- **鉴别诊断**：期望疾病列表逐条匹配算召回率；排序题另算 MRR。
- **检查决策**：题干内嵌 A/B/C/D 且参考答案写了「答案是X」的按选项判；其余按句子级要点覆盖（阈值 0.45）。

三级 AI 复核（`eval/ai_judge.py`、`eval/judge.py`）：

- 开放题给判分器看「题目 + 材料 + 参考答案 + 参考要点 + 模型回答」，输出
  `verdict`（correct / partial / wrong）、`score`（1 / 0.5 / 0）、`same_disease`、`missing`、`hallucination`、`reason`；
- 判分器看不到模型身份，温度 0，结果按「题号 + 回答哈希」缓存；
- `partial` 表示方向对但不够精确（只答到上位诊断、漏掉合并诊断、鉴别诊断只覆盖一部分），
  报告里既有**严格准确率**，也有**平均得分（含部分分）**；
- 只判「字符串不一样」是不够的：诊断名有同义词与上下位关系（例如模型答「嵌顿性腹股沟疝」、
  参考答案是「嵌顿性腹股沟斜疝合并肠梗阻」，严格相等会判错，AI 判 partial 更合理）；

- D09–D11 的 65 道 rubric 题用 DeepSeek（`deepseek-chat`，温度 0，JSON 输出）逐条判 criterion 是否满足；
- 归一化分 = 命中的正分之和 ÷ 正分总分（负分命中直接扣），踩雷题数单独统计；
- 密钥只在运行时从 `~/.codex/config.toml` 读取，不写入项目、不打印；
- 判分结果按题落盘缓存，重跑不重复调用接口。

### 引用可追溯率怎么算（`eval/traceability.py`）

L2/L3/L5 的提示词把检索结果按 `[1] [2] …` 编号，并要求模型用
`[chunk_id: kb::<doc>::<hash>]` 标注依据。两种写法都认：

- 显式 chunk_id（含裸 `kb::…::…`）；
- 资料编号 `[1]`／`【1】`，按本轮检索结果**有序**映射回 chunk_id。

分子的口径是「引用的 chunk_id 确实出现在本轮检索结果里」= 可定位；「可支撑」
需要 AI 判分或人工抽检。**注意**：跨语言、跨卷检索会让模型引到「另一个也讲这个病」
的块，那不算编造，但会算进一个不同的口径里——见 `kb/README.md` §8.2。

> 2026-09-14 修复：旧正则的字符集不包含冒号，`kb::baike-38::3badd7513c40` 这类真实
> chunk_id 一个都匹配不到，导致该项指标恒为 0.0%。修复后同一批 L3 结果从 0.0% → 76.2%。

### 两个会「静默产出错误实验」的坑（都已修）

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| 预检索半成品被复用 | 一次被中断的 L3 只写了 19 题 `contexts.jsonl` 就死了；重跑时 `ensure_contexts` 发现行数不够去调 `stage_retrieve`，而后者见到文件存在直接跳过，于是 298 道题拿到的都是「本轮未检索到相关资料」，整轮实验静默失真 | `ensure_contexts` 改为**按题号**检查覆盖，缺题就带 `force=True` 重跑，重跑后仍缺直接报错退出（`tests/test_eval_contexts.py`） |
| 引用解析匹配不到 chunk_id | 指标恒为 0，看起来像「模型从不引用」，实际是正则不含冒号 | 见上一节 |

教训：**跑完 L2/L3 先看 `contexts.jsonl` 的行数与平均证据条数**，再看分数。
正例：L2 那轮 312 题、每题 5 条证据；反例：被污染那轮的 19 行。

### 生成协议 `thinkcap-v1`（2026-09-14）

接入知识库后慢思考开始打转，312 题里 168 题跑满预算、答案根本没写出来。
现在的协议是「**预算适度放宽 + 思考有硬上限 + 掐断后补答一次**」：

| 环节 | 规则 | 位置 |
| --- | --- | --- |
| 输出预算 | 接入知识库的层（L2/L3/L5）+768 token；快思考仍按 60% 给但保底 640 | `run_eval.token_budget` |
| 思考上限 | 慢思考最多用掉输出预算的一半（保底 512） | `run_eval.think_budget_for` |
| 退化检测 | 思考块内出现 24-gram 复读（紧挨着重复，或窗口内重复 ≥3 次）即掐断 | `pangu_infer.stop_reason_for` |
| 掐断方式 | 逐行强制 EOS，同批其它行照常跑完 | `pangu_infer.chat_batch` |
| 补答 | 被掐断的题用**快思考**+「先给一行结论」重跑一次（预算 640，每题最多补一次） | `run_eval.stage_generate` |

两条设计说明：

1. **重复检测只在思考块内生效**。正式答案里本来就有列表、表格、同类句式，
   24-gram 撞一次是常态；早期版本在答案段也判，把一份写得正好的答案判成打转丢掉
   （实测踩到）。现在的门槛是「紧挨着复读」或「窗口内 ≥3 次」。
2. **快思考补答会损失推理**，所以只在「不补就一定是错」的前提下才用它；
   预测里用 `rescued` 单独标记，报告里可以剔除这一部分单独看。

`predictions.jsonl` 新增两个字段：`stop_reason`（natural / think_cap / repeat / max_tokens）、
`rescued`；`truncated` 的含义也改了——从「跑满预算」改成「最终没拿到任何回答」，
这样救援成功的题不会被算进截断。

实测（6 道此前必错的 D12 计算题）：掐断 6/6，补答 6/6，补答后判对 1 道。
——**它把「必然错」变成「有对有错」，但仍不是「答得好」**；真正的提升要靠别的手段。

上报指标（写在 `summary.md` 顶部）：

| 指标 | 口径 | 适用层 |
| --- | --- | --- |
| 准确率 | 可自动判分题目中判对的比例（严格口径，partial 算不对） | 全部 |
| 平均得分 | 含部分分：correct=1、partial=0.5、wrong=0 | 全部 |
| 安全合规率 | D09–D11 中未踩负分条目的比例（需先跑 judge 阶段） | 全部 |
| 引用可追溯率 | **知识库模块专属指标**：结论能在知识库里真实溯源的比例。基线没有检索与引用，按约定固定为 **0**；L2/L3/L5 接入检索后，用 `eval/traceability.py` 校验真实 chunk_id（可定位 + 可支撑） | 仅 L2 / L3 / L5 |

**暂不设为上报指标的**（原始判定仍留在 `scores.jsonl`，需要时可查）：

| 指标 | 为什么不报 |
| --- | --- |
| 幻觉率 | 口径未定（事实性幻觉难以有公认金标准），暂不设置，避免出现说不清分母的"数字" |
| D13 材料引用合规率 | 测的是题目自带材料时会不会指认来源，与知识库溯源不是一回事，不列为上报指标；D13 的**维度准确率**照常统计 |

## 五、速度与稳定性

单条解码只有 37 tok/s 且算力几乎闲置；批处理能把整卡吞吐拉到十几倍。方案固定了四件事：

1. **批处理**：默认 `--batch-size 32`。实测（128 token 输出）batch 32 → 649 tok/s，batch 64 → 1158 tok/s，详见 `模型部署说明.md` §五之三。
2. **按题型分组 + 组内按长度排序**：一批之内同题型、同输出预算，减少 padding，也避免长题型被短题型的预算截断。
3. **预热**：模型加载后先跑一次 8 token 调用，把昇腾算子首次编译的 5–7 秒放在计时之外。
4. **断点续跑**：`predictions.jsonl` 按「题号 + 配置指纹」去重，中断后重跑只补没做完的题。

每题都有输出预算（见 `eval_lib.MAX_NEW_TOKENS`），触顶会在结果里标 `truncated`，报告单列「截断」列。截断说明预算不够，应调大重跑该题，不能当成模型答错。

**关于截断（2026-09-13 修订）**：慢思考会先写完整推理再给结论，早先的预算偏小，实测 312 题里 180 题触顶、分数虚低。
现在按实测把预算调到：单选 1536、计算 3072、证据问答 1280、开放诊断/鉴别 1536、检查决策 2048、rubric 2560（快思考按 60% 给、保底 640）。
同时生成阶段会自动**重跑上次被截断的题**，判分缓存也按「题号 + 回答哈希」失效——回答变了就重判，不会沿用旧判定。

### 估时（312 题）

| 模式 | 预计输出 | 估时 | 说明 |
| --- | --- | --- | --- |
| 慢思考（默认） | 约 21.2 万 token | 约 5 分钟 | 带思考过程，答案质量更好 |
| 快思考（`--thinking fast`） | 约 15.9 万 token | 约 3 分钟 | 自动在输入末尾加 `/no_think` |

外加：模型加载约 7 秒；rubric 判分 65 题串行调 DeepSeek 约 20–25 分钟（与生成分开跑）。

## 六、复现性约定

1. **贪心解码**：`do_sample=False`，无随机性。
2. **固定批大小**：批大小会轻微影响贪心结果（bf16 累加顺序不同），一次实验内必须固定；不要把单条结果和批处理结果混在一张表里。
3. **固定提示词版本**：模板改动要升 `PROMPT_VERSION`，否则新旧结果不可比。
4. **配置指纹**：每条预测都带指纹（层级 / 思考模式 / 批大小 / 提示词版本 / 数据集），分数只汇总同指纹的结果。
5. 同一批配置下结果确定：同进程两次、跨进程两次的输出指纹一致（已验证）。

## 七、命令手册

**最省事的方式：一键脚本**（在终端直接跑，默认跑慢思考 + 快思考两种模式并给出对比）

```bash

bash /data/openpangu/run_eval.sh --watch     # 同上 + 实时看板（推荐）
```

## 八、质量保障

1. **难度探针**：L0 跑完后标出「全对」和「全错」的题，前者没区分度，后者多半题目有问题。
2. **机器判分是近似**：开放题用名称相似度与要点覆盖，会误判。正式报告建议 D03 / D04 / D05 各抽 10–15 题人工复核，或改用双人 1–5 分。
3. **rubric 判分留痕**：每条 criterion 的判定理由都在 `rubric_judgments.jsonl`，有争议直接复核。
4. **置信区间**：报告给 Wilson 95% CI。15 题的维度半宽约 ±25 个百分点，别拿两个小维度的均值直接相减。
5. **重复跑**：同一层建议跑 3 次看方差；本方案贪心解码，方差主要来自批组成变化，建议固定批大小与题序。

## 九、已知局限

1. D07（15 题）需要模拟患者，D13 检索（5 题）需要 A 线检索器，本版跳过并记录原因。
